## 1. 相談の要旨

部活・サークルの学外活動届を電子化する Web アプリケーションを開発しました (要件定義書 v3.0 に基づく)。
現在はローカル環境で検証を終えた段階で、**大学の Azure サブスクリプション上での試験運用**に進みたく、次の 3 点についてご相談します。

1. Azure App Service を利用したアプリケーションの配置 (リソースグループの払い出しと権限付与)
2. Entra ID による認証 (App Service の組み込み認証機能を利用。アプリ登録 1 件が必要)
3. ソースコードの管理場所 (GitHub Organization または学内で定められたリポジトリ)

## 2. 業務の概要

| 項目 | 内容 |
|---|---|
| 目的 | 学外活動 (大会・合宿等) の活動情報・現地責任者・参加者名簿を把握し、平時の確認と有事の初動を支える |
| 利用者 | 学生 (団体代表者、約 N 団体)、学生支援課職員 (数名)、管理職、顧問教員 |
| 業務量 | 活動届 年間数百〜数千件、年度部員名簿 年 1 回 |
| 現状 | 紙・メール・個別ファイルで分散管理 |
| 主な機能 | 活動届の提出、事前確認対象 (宿泊・海外・運転・危険活動) の職員確認、差戻し・再提出、年度部員名簿の登録、有事用ダッシュボード |

## 3. システム構成

### 3.1 アーキテクチャ

```
利用者ブラウザ ──HTTPS──► Azure App Service (Linux, Python 3.12)
                            ├ 組み込み認証 (Entra ID) … 未認証要求は 302 でログインへ
                            ├ アプリケーション (FastAPI / gunicorn)
                            ├ DB: SQLite (/home/data、試験運用) → PostgreSQL Flexible Server (本番)
                            └ 添付ファイル: /home/data (試験運用) → Blob Storage (本番)
GitHub (main ブランチ) ──GitHub Actions──► App Service へ自動配備
```

### 3.2 技術スタック

| 層 | 技術 | 備考 |
|---|---|---|
| 言語・フレームワーク | Python 3.12 / FastAPI / Jinja2 (サーバー側描画) | 外部 JavaScript ライブラリ・CDN への依存なし |
| DB | SQLAlchemy 2 + Alembic (スキーマ版管理) | SQLite → PostgreSQL は接続文字列の変更のみ |
| 認証 | App Service 組み込み認証 (Easy Auth) + Entra ID | アプリ側でトークン・シークレットを扱わない |
| 配備 | GitHub Actions → App Service (Oryx ビルド) | push 時に自動テスト (pytest) と静的解析 (ruff) を実行 |
| 依存ライブラリ | fastapi, sqlalchemy, alembic, jinja2, openpyxl, markdown, gunicorn, psycopg 等 | `requirements.txt` に明記。すべて OSS (MIT/BSD/LGPL) |

### 3.3 外部通信

アプリケーションからの外部通信は **ありません** (メール送信は未実装。実装時は Microsoft Graph を想定し、別途相談)。
利用者からの入力は HTTPS のみ。App Service の既定ドメイン (`*.azurewebsites.net`) と無料の管理証明書を使用。

## 4. 取り扱う情報と保護措置

### 4.1 情報の分類

| 区分 | 項目 | 該当する取扱い |
|---|---|---|
| 個人情報 (学生) | 学籍番号、氏名、所属、学年 (名簿) | 要保護。閲覧を指定職員・管理職に限定 |
| 個人情報 (学生・教職員) | 現地責任者の氏名・携帯番号・メール、申請者のメール | 届の閲覧権限に準ずる |
| 業務情報 | 活動内容、日時、場所、行程表等の添付 | 学内限り |
| 要配慮個人情報 | **取り扱わない**。名簿は「学籍番号・氏名・所属・学年」の 4 列に固定し、それ以外の列を含むファイルは取り込みを拒否する | 要件定義書 3.3 |

### 4.2 保護措置

| 観点 | 措置 |
|---|---|
| 保管場所 | Azure Japan East (東日本)。国外へ転送しない |
| アクセス制御 | 役割ベース (学生 / 顧問 / 指定職員 / 管理職 / 保守)。画面のみならずサーバー側で毎要求を判定 |
| 名簿の分離 | 名簿は届の一般情報と別テーブル・別権限。顧問・保守担当には表示しない。学生は自団体の名簿のみ |
| 監査 | 提出・再提出・状況変更を監査ログに記録 |
| 認証 | 大学の Entra ID アカウントのみ (テナント限定)。パスワードをアプリで扱わない |
| 通信 | HTTPS 強制、セッション Cookie は Secure/HttpOnly/SameSite=Lax |
| 開発時 | 実在の個人情報をテストデータ・リポジトリに含めない。DB・添付・設定ファイルは Git 管理対象外 |
| 保存期間 | 未確定 (要件定義書 14 章)。個人情報保護方針に沿って別途決定し、年度アーカイブ機能を追加予定 |

## 5. 認証・認可の設計

- App Service の「認証」機能を有効化し、ID プロバイダーに Microsoft (Entra ID、当テナントのみ) を設定する。
- 未認証要求は Entra ID のログインへリダイレクトされ、認証済み要求のみアプリケーションに到達する。
- アプリケーションは App Service が付与するヘッダー (`X-MS-CLIENT-PRINCIPAL-NAME` 等) から利用者を識別する。
- 役割の決定: 職員・管理職・保守担当はアプリ設定 (環境変数) のメール一覧、顧問は団体台帳の顧問メール、それ以外の大学アカウントは学生。
- 将来、Entra ID のグループやアプリロールによる役割付与に切り替えることも可能 (設計上の変更点は 1 ファイル)。

### 必要となる Entra ID のアプリ登録

| 項目 | 値 |
|---|---|
| 名前 | activity-safety-app (仮) |
| サポートされるアカウント | この組織のディレクトリのみ (シングルテナント) |
| リダイレクト URI | `https://<アプリ名>.azurewebsites.net/.auth/login/aad/callback` |
| 資格情報 | クライアント シークレット (App Service の認証設定に格納。アプリコードには含めない) |
| API アクセス許可 | `User.Read` (既定) のみ。メール送信を実装する場合は別途 `Mail.Send` を相談 |

App Service の認証設定画面から自動作成できる場合は、そちらで作成します。テナントの設定でアプリ登録が制限されている場合は、上記内容での作成をお願いします。

## 6. 必要な Azure リソースと権限

### 6.1 試験運用および本番 (当面)

| リソース | SKU / 設定 | 月額目安 |
|---|---|---|
| リソース グループ | `rg-activity-safety` (Japan East) | － |
| App Service プラン | Linux, Basic B1 (1 vCPU / 1.75 GB)、Always On 有効 | 約 2,000〜2,500 円 |
| Web アプリ | Python 3.12、組み込み認証 有効、ヘルスチェック `/healthz`、日次バックアップ | (プランに含む) |
| Entra ID アプリ登録 | 5 章のとおり | 無料 |
| (任意) Application Insights | 監視・エラー通知 | 無料枠内 |
| (任意) 予算アラート | 月額上限の通知 | 無料 |

想定規模 (活動届 年数千件、同時利用 数十人) では Basic B1 で本番運用可能と考えています。年額約 3 万円。

### 6.2 将来の拡張時 (必要になった場合のみ)

| リソース | SKU | 月額目安 | 契機 |
|---|---|---|---|
| App Service プラン | Basic B2 または Premium P0v3 | 約 4,500〜10,000 円 | 応答が遅い、同時利用が増えた |
| Azure Database for PostgreSQL Flexible Server | Burstable B1ms、32 GB、自動バックアップ 7 日 | 約 2,000〜4,000 円 | 複数インスタンス化、DB の分離 |
| ストレージ アカウント (Blob) | 添付ファイル用 | 数十〜数百円 | 同上 |

金額は概算です。教育機関向け契約の割引は考慮していません。

### 6.3 依頼したい権限

| 対象 | 権限 | 対象者 |
|---|---|---|
| リソース グループ `rg-activity-safety` | 共同作成者 (Contributor) | 学生支援課の担当者 2 名 |
| サブスクリプション | 閲覧者 (コスト確認のため。任意) | 同上 |
| Entra ID | アプリ登録の作成 (または貴部門で作成) | － |

## 7. ソースコードの管理

- 現在は開発者個人の GitHub アカウント配下 (非公開) にあります。**大学名義の GitHub Organization、または学内規程で定められたリポジトリへの移管**を希望します。
- 学内標準が GitHub Copilot であるため、GitHub Organization を第一候補と考えています (Copilot の Issue 自動対応・コードレビュー機能と連携するため)。
- リポジトリには個人情報を含めません (DB・添付・設定ファイルは Git 管理対象外)。要件定義書 (学内限り) を含むため非公開設定とします。
- 変更管理: Pull Request → 自動テスト (受入シナリオ 18 件) と静的解析 → レビュー → main へマージ → Azure へ自動配備。

## 8. 運用体制 (案)

| 項目 | 内容 |
|---|---|
| 業務主管 | 学生支援・課外活動担当 |
| システム保守 | 学生支援課の担当者 2 名 (GitHub Copilot を利用)。設計書・開発手順書はリポジトリ内に整備済み |
| 監視 | App Service のヘルスチェック、ログストリーム、(任意) Application Insights のアラート |
| バックアップ | 試験運用: App Service のバックアップ機能。本番: PostgreSQL の自動バックアップ |
| 更新 | GitHub main への push で自動配備。DB スキーマ変更は Alembic で自動適用 |
| 障害時 | 自動処理が停止しても、職員が画面から手動で受付・通知できる縮退運用を設計済み |
| 削除防止 | リソース グループに削除ロックを設定 |

## 9. スケジュール (案)

| 時期 | 内容 |
|---|---|
| 相談後 2 週間 | リソース払い出し、Entra ID アプリ登録、リポジトリ移管 |
| その後 1 週間 | App Service 配置、認証設定、職員による受入確認 |
| 次の 1〜2 か月 | 少数団体でパイロット (要件定義書 13 章 段階 7) |
| パイロット後 | 本番構成 (PostgreSQL 等) への移行、全団体展開 |

## 10. ご相談・ご判断いただきたい事項

1. Azure サブスクリプションでのリソース払い出しと権限付与 (6.3) の可否と手順

3. ソースコードの管理場所 (7 章): 大学の GitHub Organization の有無、利用条件
4. 個人情報 (4.1) を Azure (Japan East) に保管することについての学内手続き (個人情報保護担当への届出等の要否)
5. データの保存期間 (要件定義書 14 章) の決定に関わる部署
6. 将来のメール通知 (Microsoft Graph `Mail.Send`) の実現方式
