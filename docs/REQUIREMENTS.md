課外活動安全管理システム

要件定義書

Microsoft Lists Formsを入口とする最小実装

| 項目 | 内容 |
|---|---|
| 版数 | v3.0（議論反映版） |
| 作成日 | 2026年9月4日 |
| 対象 | 部活・サークルの学外活動届、年度部員名簿 |
| 主管 | 学生支援・課外活動担当 |
| 取扱 | 学内限り |

> この版の主要決定 活動届はSharePointリストに紐づくMicrosoft Lists Formsで受け付ける。対象活動の参加者名簿提出、および年1回の年度部員名簿提出は維持する。

## 1. 文書の目的と位置付け

本書は、大学公認の部活・サークル等が行う学外活動について、活動情報、現地責任者、参加者名簿等を適切に把握し、平時の確認と有事の初動を支えるための業務・システム要件を定める。

> 基本方針 安全管理を弱めず、学生・職員双方の入力・転記負担を抑える。入力は分かりやすく、管理情報は裏側で保持し、例外的な高リスク活動は職員が事前確認する。

### 1.1 背景

- 学外活動に関する情報が紙、メール、個別ファイルに分散すると、有事の検索性と確認速度が低下する。
- 一方、すべての活動を重い承認フローにすると、学生・職員双方の負担が増え、形骸化しやすい。
- 参加者名簿は危機対応・保険実務上の重要情報であるため、対象活動ごとの提出要件を維持する。
- 年度部員名簿は、所属者・公認団体・保険等の基礎管理に用いるため、年1回の提出を維持する。

### 1.2 設計原則

| 原則 | 内容 |
|---|---|
| 安全性 | 対象活動では行程等と参加者名簿を提出し、職員が事前確認する。 |
| 簡素性 | 活動届はLists Formsから活動届リストへ直接登録し、不要な転記処理を作らない。 |
| 入力配慮 | 学生に団体ID等の内部コードを入力させない。 |
| 最小権限 | 参加者名簿は通常の活動情報より厳しい権限で管理する。 |
| 人の判断 | 高リスク活動の妥当性判断は自動承認せず、職員が確認する。 |
| 縮退可能 | 自動化停止時もリスト・手動通知で業務継続できる。 |

## 2. 対象範囲

### 2.1 対象業務

| 業務 | 対象 | 提出単位 | 主目的 |
|---|---|---|---|
| 学外活動届 | 学外で行う活動 | 活動ごと | 活動概要と緊急連絡先の把握 |
| 対象活動の追加資料 | 宿泊・海外・学生運転・通常より危険な活動 | 活動ごと | 事前確認と有事対応 |
| 年度部員名簿 | 公認団体等 | 年度初めに年1回、必要時更新 | 所属者・保険・団体管理の基礎 |

### 2.2 対象外・将来検討

- 学内で行う通常の練習、ミーティング等の個別届出
- 事故記録専用データベース、複雑な承認ワークフロー、学生向け申請履歴ポータル
- 活動ごとの自動リスクスコアリング、帰着確認の全件自動化
- Power Appsによる高度な動的必須制御。必要性が顕在化した段階で再評価する。

## 3. 業務ルール

### 3.1 活動区分

| 区分 | 該当条件 | 提出物 | 大学の扱い |
|---|---|---|---|
| 通常の学外活動 | 下記の事前確認対象に該当しない活動 | 活動届 | 受付・記録 |
| 事前確認対象 | 宿泊または海外を伴う／学生が車両を運転する／山岳・水辺・火気等、通常より危険を伴う | 活動届、行程表・活動計画書等、参加者名簿 | 職員が事前確認し、確認済または差戻しを通知 |

### 3.2 名簿の二層管理

| 名簿 | 対象者 | 提出時期 | 扱い |
|---|---|---|---|
| 年度部員名簿 | 団体に所属する学生 | 年1回。加入・退部等で必要がある場合は更新 | 活動届とは別業務として回収・保管 |
| 活動参加者名簿 | 当該活動に実際に参加する予定の学生 | 事前確認対象の活動ごと | 活動届に添付し、限定された保管先へ移送 |

> 重要 年度部員名簿を提出済みであっても、対象活動ごとの参加者名簿提出は省略しない。両者は目的と対象時点が異なる。

### 3.3 名簿の記載項目

- 最低限：学籍番号、氏名、所属、学年
- 記載させない情報：病歴、障害情報、常用薬、保護者連絡先その他の要配慮情報
- 参加者変更時は、活動実施前に担当部署へ連絡し、必要に応じて差替える。

## 4. 利用者と権限

| 利用者 | できること | できないこと |
|---|---|---|
| 学生・団体代表者 | Lists Formsから活動届を提出する | 活動届リストや他団体の回答を閲覧する |
| 顧問 | 必要に応じ通知を受け、団体へ指導する | 名簿保管先を常時閲覧する |
| 指定職員 | 活動届確認、状況更新、差戻し、名簿確認 | 権限外の目的で個人情報を利用する |
| 管理職・危機管理担当 | 必要時の閲覧、状況把握 | 日常運用上不要な編集を行う |
| システム保守担当 | フロー・列・権限の保守 | 業務目的なく名簿内容を閲覧する |

## 5. システム構成

| 構成要素 | 役割 | 配置 |
|---|---|---|
| Microsoft Lists Forms | 学生向け活動届入力画面 | 活動届リストに紐付け |
| 活動届リスト | 届出情報の正本データ | 課外活動申請サイト |
| 団体台帳 | 団体名、団体ID、代表者・副代表者・顧問、有効状態の管理 | 課外活動申請サイト |
| 活動資料 | 行程表、大会要項等の保管 | 課外活動申請サイト |
| 参加者名簿保管先 | 活動参加者名簿・年度部員名簿の限定保管 | 個人情報管理サイト |
| Power Automate | 発番、照合、条件検査、通知、添付振分け | Microsoft 365標準コネクタ |

> アーキテクチャ決定 独立したMicrosoft Formsから活動届リストへ転記する方式は採用しない。Lists Formsから活動届リストへ直接登録し、自動化は受付後処理に限定する。

## 6. 活動届フォーム要件

### 6.1 表示項目

| No. | 表示名 | 列型 | 必須 | 入力上の注意 |
|---|---|---|---|---|
| 1 | 所属する団体 | 団体台帳へのLookup | 必須 | 団体名を選択。団体IDは学生に表示・入力させない |
| 2 | 活動内容 | 複数行テキスト | 必須 | 大会名、合宿名、目的等が分かるようにする |
| 3 | 開始日時 | 日時 | 必須 | 活動開始日時 |
| 4 | 終了日時 | 日時 | 必須 | 宿泊等は帰着または団体解散予定を含む |
| 5 | 活動場所・宿泊先 | 複数行テキスト | 必須 | 施設名、所在地、複数場所、宿泊先 |
| 6 | 参加予定人数 | 数値 | 必須 | 学生、教職員、指導者等を含む合計 |
| 7 | 現地責任者氏名 | テキスト | 必須 | 活動中に連絡可能な者 |
| 8 | 現地責任者携帯番号 | テキスト | 必須 | 数値型にしない |
| 9 | 現地責任者メール | テキスト | 必須 | 学内メール |
| 10 | 事前確認対象 | はい／いいえ | 必須 | 該当条件を質問文に列挙 |
| 11 | 行程等の概要 | 複数行テキスト | 任意 | 対象活動のみ入力する旨を明記 |
| 12 | 添付書類確認 | 複数選択Choice | 任意 | 行程等／参加者名簿を自己申告 |
| 13 | 添付ファイル | 添付 | 任意 | 対象活動では実質必須。自動検査で補う |
| 14 | 大学への連絡事項 | 複数行テキスト | 任意 | 安全配慮・懸念等 |

### 6.2 内部管理項目

| 項目 | 設定・用途 |
|---|---|
| 申請番号 | 自動発番。ACT-{リストID}等の一意値 |
| 団体ID | Lookup先の団体台帳から自動取得 |
| 申請者氏名・メール | 登録者情報から取得 |
| 申請者確認 | 一致／要確認／照合不可 |
| 状況 | 未確認／確認済／差戻し／中止／完了 |
| 備考 | 差戻し理由、職員の申し送り、個別指示 |
| 作成元 | Lists Forms等、登録経路の識別 |

### 6.3 表示・必須制御の方針

- Lists Formsの分岐は、不要な質問を経路上で飛ばす目的に限定して利用を検討する。
- 同一項目の必須・任意を回答に応じて動的変更する実装には依存しない。
- MVPでは追加項目を「該当する場合のみ入力・添付」と明記し、対象活動なのに不足がある場合は受付後の自動検査または職員確認で差戻す。
> UX上の割り切り 追加項目が画面上に見える場合でも、フォーム構成を過度に複雑にしない。入力説明を明確にし、不足検知を後処理で補う。

## 7. 団体選択・団体台帳要件

### 7.1 団体選択

- 学生に団体IDを自由入力させない。
- 団体数が多いため、固定Choiceの大量管理ではなく、団体台帳へのLookupを第一候補とする。
- 学生には団体名を表示し、内部ではLookup IDおよび団体IDで一意に識別する。

### 7.2 団体台帳

| 項目 | 型 | 用途 |
|---|---|---|
| 団体名 | タイトル／テキスト | 学生向け表示名 |
| 団体ID | 1行テキスト | 改称に影響されない不変キー |
| 代表者メール | 1行テキスト | 申請者照合 |
| 副代表者メール | 1行テキスト | 申請者照合、任意 |
| 顧問メール | 1行テキスト | 通知先 |
| 有効フラグ | はい／いいえ | 休止・廃止団体の管理 |

- Lookup候補を有効団体だけに限定できない場合は、MVPでは有効団体台帳とアーカイブを分ける運用を選択肢とする。

## 8. 自動化要件

### 8.1 受付後処理フロー

| 順序 | 処理 | 要件 |
|---|---|---|
| 1 | 項目作成を検知 | 活動届リストに項目が作成されたときに開始 |
| 2 | 申請番号付与 | 一意の申請番号を設定 |
| 3 | 団体情報取得 | Lookup先の団体台帳から団体ID、代表者、副代表者、顧問を取得 |
| 4 | 申請者照合 | 登録者メールと代表者・副代表者メールを比較 |
| 5 | 不足検査 | 対象活動で、添付なし、行程等未選択、参加者名簿未選択等を検査 |
| 6 | 添付振分け | 行程等は活動資料、参加者名簿は個人情報管理サイトへ保存 |
| 7 | 受付通知 | 通常活動は受付完了、対象活動は確認中として申請者へ通知 |
| 8 | 確認依頼 | 対象活動は指定職員へ通知し、必要に応じ顧問へ共有 |

### 8.2 判定ルール

| 条件 | 処理 |
|---|---|
| 申請者メール＝代表者または副代表者 | 申請者確認＝一致 |
| 団体台帳に代表者・副代表者メールがない | 申請者確認＝照合不可 |
| 上記以外 | 申請者確認＝要確認、職員へ通知 |
| 事前確認対象＝いいえ | 通常受付通知 |
| 事前確認対象＝はい、必要資料あり | 状況＝未確認、職員へ確認依頼 |
| 事前確認対象＝はい、必要資料不足 | 状況＝差戻し、不足内容を申請者へ通知 |

### 8.3 結果通知フロー

- 職員が状況を「確認済」または「差戻し」に変更した場合のみ申請者へ結果通知する。
- 差戻し時は備考欄の理由を通知本文へ含める。
- 同一値の再保存等による重複通知を抑止する。
- 山岳・海外・水辺等で帰着連絡が必要な場合は、確認結果通知と備考に個別指示を記録する。

## 9. 情報管理・セキュリティ要件

| 要件 | 内容 |
|---|---|
| 最小権限 | 活動届サイトと名簿保管サイトの閲覧者を分離し、名簿は課長・指定職員等に限定する。 |
| 学生の閲覧制限 | 学生はフォームから投稿できるが、リスト本体・他団体回答・名簿保管先を閲覧できない。 |
| 個人情報分離 | 活動概要と参加者名簿を同一の一般閲覧範囲に置かない。 |
| 入力制限 | 名簿に病歴、障害情報、常用薬、保護者連絡先等を記載させない。 |
| 監査性 | リスト・ライブラリのバージョン履歴を有効化し、更新者・更新日時を保持する。 |
| 所有者 | 個人アカウント依存を避け、サービスアカウントまたは組織管理下の所有にする。 |
| 保存期間 | 学内規程、保険実務、個人情報保護方針と整合させて別途確定する。 |

## 10. 非機能要件

| 分類 | 要件 |
|---|---|
| 可用性 | Microsoft 365の標準機能を用い、過度なカスタマイズを避ける。 |
| 操作性 | 学生がスマートフォンから入力でき、内部コードを知らなくても提出できる。 |
| 保守性 | 列名・選択肢・台帳の二重管理を抑え、団体情報は団体台帳を正本とする。 |
| 性能 | 通常の大学課外活動届件数で支障なく検索・表示できること。件数増加時はインデックスと年度アーカイブを検討する。 |
| 障害対応 | フロー停止時もリストの登録内容を基に手動受付・手動通知できる。 |
| 監視 | フローの失敗通知と定期的な実行履歴確認を行う。 |
| アクセシビリティ | 質問文は平易な日本語とし、略語・専門用語を避ける。 |

## 11. 画面文言案

### 11.1 フォーム冒頭

> 部活・サークル 学外活動届 部活・サークルが学外で活動する場合に提出してください。学内で行う通常の練習・ミーティング等は提出不要です。宿泊・海外、学生による車両運転、山岳・水辺・火気等、通常より危険を伴う活動では、行程表等および参加者名簿の提出が必要です。

### 11.2 事前確認対象の質問

> 今回の活動は、次のいずれかに該当しますか ・宿泊または海外を伴う・学生が自動車等を運転する・山岳、水辺、火気など、通常より危険を伴う該当する場合は「はい」を選択し、行程等の概要と必要書類を提出してください。

### 11.3 添付欄

> 必要書類を添付してください 事前確認対象の活動では、行程表・活動計画書等と参加者名簿を添付してください。名簿には、病歴、障害情報、常用薬、保護者連絡先等を記載しないでください。

### 11.4 提出後

- 提出内容の変更または活動中止が生じた場合は、担当部署へ連絡する。
- 事前確認対象の活動は、大学からの確認結果または差戻し連絡を確認する。

## 12. 受入要件・テスト

| No. | シナリオ | 期待結果 |
|---|---|---|
| 1 | 通常活動を提出 | 活動届へ直接登録され、受付完了通知が届く |
| 2 | 対象活動を必要資料付きで提出 | 活動届へ登録され、資料が適切な保管先へ保存され、確認依頼が届く |
| 3 | 対象活動を資料不足で提出 | 差戻しとなり、不足内容の通知が届く |
| 4 | 登録代表者が自団体を選択 | 申請者確認が一致になる |
| 5 | 別団体または未登録者が提出 | 要確認または照合不可となり、職員が把握できる |
| 6 | 職員が確認済へ変更 | 申請者へ結果通知が1回届く |
| 7 | 職員が差戻しへ変更 | 備考の理由を含む通知が届く |
| 8 | 学生アカウントでリストURLへアクセス | 他の活動届・名簿を閲覧できない |
| 9 | 名簿に禁止項目がない様式を提出 | 限定保管先に保存される |
| 10 | フロー停止を想定 | 登録内容から手動で受付・通知を継続できる |

## 13. 実装順序

| 段階 | 作業 | 完了条件 |
|---|---|---|
| 1 | 列・台帳整理 | 団体Lookup、内部管理列、状態値を確定 |
| 2 | Lists Forms作成 | 学生入力項目、説明、添付欄を設定 |
| 3 | 権限設定 | 学生は投稿のみ、職員・名簿閲覧者を分離 |
| 4 | 受付後処理フロー | 発番、照合、不足検査、通知、添付振分け |
| 5 | 結果通知フロー | 確認済・差戻しの変更時だけ通知 |
| 6 | 受入試験 | 通常・対象・不足・誤選択・権限の各ケース合格 |
| 7 | パイロット | 少数団体で試行し、入力負担と職員処理を確認 |
| 8 | 年度部員名簿 | 別フォーム／別保管単位で年次回収を実装 |

## 14. 未確定事項・要確認

| 項目 | 確認内容 | 決定者 |
|---|---|---|
| 保険実務 | 活動ごとの提出情報と事故証明・補償条件の整合 | 保険窓口・学生支援 |
| 保存期間 | 活動届、活動資料、参加者名簿、年度部員名簿の保存年限 | 個人情報・文書管理担当 |
| Lookup候補 | 有効団体だけをフォーム候補にできるか、実機確認 | システム担当 |
| 添付振分け | 複数添付時の行程表・名簿の識別方法 | 業務担当・システム担当 |
| 年度名簿更新 | 年1回提出後の加入・退部時の更新ルール | 学生支援 |
| 帰着連絡 | 個別指示とする活動の具体的基準 | 危機管理・学生支援 |

> 実装開始条件 未確定事項のうち、保険実務、名簿保存期間、権限範囲、添付振分け方法は、本番運用開始前に確定する。

## 15. 決定事項まとめ

- 活動届は、SharePointの「活動届」リストに紐づくMicrosoft Lists Formsで作成する。
- 学生には団体IDを入力させず、団体台帳から団体名を選ばせる。団体数が多いためLookupを基本とする。
- 宿泊・海外・学生運転・山岳・水辺・火気等の対象活動では、行程等と参加者名簿を提出する。
- 年1回の年度部員名簿提出も維持し、活動参加者名簿とは別目的・別単位で管理する。
- Lists Forms上の動的必須制御には依存せず、対象活動の資料不足は受付後処理または職員確認で差戻す。
