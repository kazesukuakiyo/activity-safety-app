# 課外活動安全管理システム (学外活動届) 設計書

| 項目 | 内容 |
|---|---|
| 対象 | 要件定義書 v3.0 (2026-09-04) に基づく Web アプリ実装 |
| 版 | 1.0 (2026-09-18) |
| 正本 | GitHub リポジトリ `docs/DESIGN.md`。コードと一緒に版管理する |
| 読者 | 学生支援課の担当者、システム保守担当、引き継ぎを受ける開発者 |

要件定義書は Microsoft Lists / Power Automate での実装を前提に書かれている。本書は、その要件を **Python (FastAPI) の Web アプリ**として実現した設計を記す。
要件の章番号を「要件 8.2」のように示し、末尾の対応表で要件・実装・テストをたどれるようにしている。

## 1. システム構成

### 1.1 要件書 5 章との対応

| 要件書の構成要素 | 本システムでの実装 |
|---|---|
| Microsoft Lists Forms (学生入力画面) | 活動届フォーム画面 `/reports/new` |
| 活動届リスト (正本データ) | DB テーブル `activity_reports` |
| 団体台帳 | DB テーブル `organizations` + 団体台帳画面 `/orgs` |
| 活動資料 (行程表・大会要項) | ファイル保管領域 `DATA_DIR/activity_docs/` |
| 参加者名簿保管先 (個人情報管理サイト) | DB テーブル `participants` / `members`。名簿はファイルではなく 4 列の表として保持し、閲覧権限で分離する |
| Power Automate (発番・照合・不足検査・通知・振分け) | 業務ロジック `app/services/intake.py` |
| メール通知 | 通知テーブル `notifications` に記録し「通知」画面で確認。メール送信は差し替え点として分離 |
| Entra ID 認証 | Azure App Service の認証機能 (Easy Auth)。ローカル検証では疑似ログイン |

### 1.2 技術構成

| 層 | 採用技術 | 理由 |
|---|---|---|
| Web フレームワーク | FastAPI + Jinja2 (サーバー側描画) | 小規模・少人数保守向き。JavaScript は補助的にのみ使用 |
| DB | SQLAlchemy 2 + SQLite (本番は PostgreSQL) | 接続文字列の変更だけで切替可能 |
| スキーマ管理 | Alembic | 本番データを保持したままテーブル変更できる |
| 名簿ファイル | openpyxl | Excel テンプレートの生成と読み取り |
| 認証 | Azure App Service Easy Auth (本番) / セッション Cookie (ローカル) | アプリ側にシークレット不要 |
| 配備 | Azure App Service (Linux, Python 3.12) + GitHub Actions | push で自動配備 |
| 品質 | pytest (受入シナリオ) + ruff + GitHub Actions CI | 変更のたびに自動検証 |

### 1.3 配置図

```
[学生・職員のブラウザ] --HTTPS--> [Azure App Service]
                                    ├ 認証 (Entra ID)  … ログイン済みの利用者だけがアプリに到達
                                    ├ アプリ (gunicorn + FastAPI)
                                    ├ DB (SQLite @ /home/data → 将来 PostgreSQL)
                                    └ 添付ファイル (/home/data/activity_docs → 将来 Blob Storage)
[GitHub main ブランチ] --push で自動配備--> [Azure App Service]
```

## 2. 利用者と権限 (要件 4 章・9 章)

役割はログインした人のメールアドレスから決まる (3 章参照)。権限は `app/auth/base.py` の `User.can_*` に集約し、画面と処理の両方で同じ判定を使う。

| 操作 | 学生 | 顧問 | 指定職員 | 管理職 | 保守担当 |
|---|---|---|---|---|---|
| 活動届を提出・再提出 | ○ (自分の分) | － | － | － | － |
| 活動届を閲覧 | 自分の分 | 担当団体の分 | 全件 | 全件 | 全件 |
| 状況を更新 (確認済・差戻し等) | － | － | ○ | － | － |
| 参加者名簿を閲覧 | 自分が入力した分 | － | ○ | ○ | － |
| 参加者名簿を CSV 出力 | － | － | ○ | ○ | － |
| 年度部員名簿を登録 | 自分が代表者・副代表者の団体 | － | ○ (代理取込) | － | － |
| 年度部員名簿を閲覧 | 自分が代表者・副代表者の団体 | － | 全団体 | 全団体 | － |
| 団体台帳を編集 | － | － | ○ | － | ○ |
| ダッシュボード | － | － | ○ | ○ | － |
| 設計書・手順書を閲覧 | － | － | ○ | ○ | ○ |

- メニューを隠すだけでなく、URL を直接開いてもサーバー側で権限を確認し、権限が無ければ 403 を返す。
- 「自分が代表者・副代表者の団体」は団体台帳の代表者メール・副代表者メールとログインメールの一致で判定する。

## 3. 認証と役割の決定

| 環境 | 方式 | 役割の決め方 |
|---|---|---|
| ローカル検証 (`AUTH_MODE=dev`) | 画面で疑似ユーザーを選ぶ | 疑似ユーザーに役割を固定 |
| Azure (`AUTH_MODE=easyauth`) | App Service の認証機能が Entra ID ログインを行い、ログイン者のメールをヘッダーで渡す | 環境変数 `STAFF_EMAILS` / `MANAGER_EMAILS` / `SYSADMIN_EMAILS` に含まれればその役割。団体台帳のいずれかで顧問メールに一致すれば顧問。それ以外は学生 |

画面・業務処理は `User` オブジェクトだけを見るため、認証方式を追加しても他は変更不要。

## 5. 業務ルール

### 5.1 状況 (要件 6.2) と遷移

```
                 通常活動                     ┌──────────────┐
  提出 ──────────────────────────────────────►│   確認済     │◄─┐
   │                                          └──────────────┘  │ 職員が変更
   │ 対象活動・資料あり   ┌──────────────┐  職員が変更          │
   ├────────────────────►│   未確認     │──────────────────────┤
   │                     └──────────────┘                      │
   │ 対象活動・資料不足   ┌──────────────┐  学生が再提出        ▼
   └────────────────────►│   差戻し     │──────────────► (再度 提出時の判定へ)
                         └──────────────┘
  職員はいつでも 中止 / 完了 に変更できる
```

| 状況 | 意味 | 誰が設定 |
|---|---|---|
| 未確認 | 事前確認対象で、職員の確認待ち | 自動 (提出時) |
| 確認済 | 通常活動の受付完了、または職員が確認した | 自動 (通常活動) / 職員 |
| 差戻し | 資料不足 (自動) または職員の判断 | 自動 / 職員 |
| 中止 | 活動が中止された | 職員 |
| 完了 | 活動が終了した | 職員 |

### 5.2 提出時の処理 (要件 8.1, 8.2)

初回提出と再提出で共通 (`intake.process_submission`)。

| 順序 | 処理 | 設計 |
|---|---|---|
| 1 | 申請番号付与 | `ACT-` + 6 桁連番 (DB の主キー)。再提出でも変わらない。版数 `revision` を +1 |
| 2 | 団体情報取得 | 団体台帳から団体ID (不変キー)、代表者・副代表者・顧問メールを取得 |
| 3 | 申請者照合 | 申請者メール = 代表者 or 副代表者 → **一致**。台帳に両方無い → **照合不可**。それ以外 → **要確認** (要件 8.2) |
| 4 | 不足検査 | 事前確認対象のみ。行程等の概要が空 / 行程表の添付なし / 参加者名簿 0 名 を不足とする |
| 5 | 状況決定 | 通常活動 → 確認済。対象活動で不足なし → 未確認。対象活動で不足あり → 差戻し (備考に不足内容を自動記載) |
| 6 | 通知 | 5.3 の一覧のとおり |
| 7 | 監査ログ | 提出 (第 n 版) として記録 |

### 5.3 通知一覧 (要件 8.1-7, 8.1-8, 8.3)

| 契機 | 宛先 | 種別 | 内容 |
|---|---|---|---|
| 通常活動を提出 | 申請者 | 受付完了 | 申請番号・活動概要 |
| 対象活動を提出 (不足なし) | 申請者 | 受付 (確認中) | 職員の確認待ちである旨 |
| 同上 | 指定職員の代表メール | 事前確認依頼 | 活動概要・現地責任者・名簿人数 |
| 同上 | 団体の顧問 | 共有 | 同上 |
| 対象活動を提出 (不足あり) | 申請者 | 差戻し (不足) | 不足項目の一覧と再提出の案内 |
| 申請者照合が 要確認 / 照合不可 | 指定職員の代表メール | 申請者確認 | 申請者と判定 |
| 職員が「確認済」に変更 | 申請者 | 結果通知 | 備考 (個別指示) を本文に含む |
| 職員が「差戻し」に変更 | 申請者 | 結果通知 | 備考 (差戻し理由) を本文に含む |

重複抑止 (要件 8.3): 結果通知は「最後に通知した状況」を記録し、同じ状況で再保存しても再通知しない。再提出があれば記録を消し、次の結果は改めて通知する。

ローカル検証と試験運用では、通知は DB に記録して「通知」画面で確認する。メール送信への切替は `notify.send()` の差し替えで行う。

### 5.4 差戻し後の再提出

- 差戻し中の届だけ、提出者本人が修正・再提出できる。
- 申請番号は変えず、版数を +1 する。前回の差戻し理由は監査ログに残す。
- 添付は既存を残したまま追加・削除でき、参加者名簿は年度名簿のチェックと追加行に振り分けて再表示する。
- 再提出後は 5.2 の判定を最初からやり直す。

## 6. 名簿の設計 (要件 3.2, 3.3, 9)

### 6.1 方針

名簿は **ファイルとして保管せず、「学籍番号・氏名・所属・学年」の 4 列の表として DB に保持する**。

| 観点 | 効果 |
|---|---|
| 要配慮情報の排除 (要件 3.3) | 入力欄が 4 列しか無い。Excel・貼り付け・行入力のどの経路でも 5 列以上の行は取り込みを拒否する |
| 有事の検索性 (要件 1) | 職員は届の画面で参加者をそのまま確認でき、ダッシュボードから場所・日付で横断検索できる |
| 添付振分けの曖昧さ (要件 14 章) | 「複数添付のどれが名簿か」という問題が生じない |
| 参加者変更 | 再提出でチェックを付け直すだけ |

### 6.2 年度部員名簿 (要件 3.2 年 1 回)

- 団体 × 年度ごとに `members` テーブルに保持。年度は 4 月始まり。
- 提出経路: (1) Excel テンプレートをダウンロード → 記入 → アップロード → プレビュー確認 → 保存、(2) Excel からの貼り付け。
- 提出者: その団体の代表者・副代表者。指定職員は受領済みの名簿を代理で取り込める。
- 保存はその年度の名簿を丸ごと置き換える (加入・退部の更新も同じ手順)。

### 6.3 活動参加者名簿 (要件 3.2 活動ごと)

- 活動届ごとに `participants` テーブルに保持 (提出時点の写し)。年度名簿を後から変えても影響しない。
- 作成方法: 年度部員名簿からチェック + 名簿に無い人を行入力 (+ 貼り付け)。学籍番号で重複排除。
- 年度名簿の提出があっても、活動ごとの参加者名簿は省略できない (要件 3.2 の「重要」)。

### 6.4 閲覧範囲

2 章の権限表のとおり。提出者本人は自分が入力した参加者を見られるが、CSV 出力 (名簿保管先の機能) は職員・管理職のみ。年度名簿は他団体分を一切表示しない (一覧にも出さない)。

## 7. データモデル

```
organizations 1──n activity_reports 1──n participants
      │                    ├──n attachments
      │                    ├──n audit_logs
      │                    └──n notifications
      └──n members
```

| テーブル | 役割 | 主な列 |
|---|---|---|
| `organizations` | 団体台帳 (要件 7.2) | 団体名、団体ID (不変キー・一意)、代表者メール、副代表者メール、顧問メール、有効フラグ |
| `activity_reports` | 活動届 (要件 6.1, 6.2) | 6.1 の 14 項目、申請番号 (一意)、団体ID、申請者氏名・メール、申請者確認、状況、備考、作成元、不足検査結果、最終通知状況、版数、初回提出・最終提出・更新日時、更新者 |
| `participants` | 活動参加者名簿 | 学籍番号、氏名、所属、学年 |
| `members` | 年度部員名簿 | 団体、年度、学籍番号、氏名、所属、学年、登録者。(団体, 年度, 学籍番号) で一意 |
| `attachments` | 添付ファイル (行程等・その他) | 種別、元ファイル名、保管パス、サイズ |
| `notifications` | 通知の記録 | 宛先、件名、本文、種別、対象の届 |
| `audit_logs` | 監査ログ (要件 9 監査性) | 対象の届、操作者、操作、詳細、日時 |
| `alembic_version` | スキーマの版 | Alembic が管理 |

列の型・制約は `app/models.py` を正とする。テーブル変更は Alembic のマイグレーションで行い、`alembic check` を CI で実行して定義との一致を保証する。

## 8. ファイル保管

| 種別 | 保管先 | 閲覧 |
|---|---|---|
| 行程表・活動計画書・大会要項・その他 | `DATA_DIR/activity_docs/<申請番号>/<乱数>_<元ファイル名>` | 届を閲覧できる人 |
| 名簿 | 保管しない (6 章のとおり表として保持) | － |

- ファイル名は安全な文字に正規化し、保管先の外を指すパスは拒否する。
- 1 ファイル 20MB まで。種類の制限は今後の課題 (11 章)。
- Azure では `/home/data` (再起動で消えない領域)。複数インスタンス化する際は Blob Storage に差し替える (`storage.py`)。

## 10. セキュリティ (要件 9 章)

| 要件 | 実装 |
|---|---|
| 最小権限・学生の閲覧制限 | 2 章の権限表。サーバー側で毎回判定 |
| 個人情報分離 | 名簿は届の一般情報とは別テーブル・別権限。顧問・保守担当には表示しない |
| 入力制限 | 名簿は 4 列固定。5 列以上を拒否 |
| 監査性 | 提出・再提出・状況更新を監査ログに記録し、届の画面に履歴表示 |
| 所有者 | Azure のリソースと GitHub リポジトリは大学名義とする (運用) |
| 通信 | 本番は HTTPS のみ。セッション Cookie は Secure 属性 |
| 秘密情報 | `.env` と `data/` は Git に含めない。実在の学生情報をテストデータに使わない |
| 保存期間 | 未確定 (要件 14 章)。年度アーカイブ機能は保存期間の決定後に設計 |

## 11. 非機能 (要件 10 章) と運用

| 分類 | 設計 |
|---|---|
| 可用性 | Azure App Service (単一インスタンス)。ヘルスチェック `/healthz` |
| 操作性 | スマートフォン幅で表をカード表示に切替。内部コード (団体ID) は学生に見せない |
| 保守性 | 団体情報は団体台帳を正本とし、届には団体IDの写しだけを持つ。業務ルールは 1 ファイルに集約 |
| 性能 | 想定件数 (年数千件) では SQLite で十分。同時利用が増えたら PostgreSQL |
| 障害対応 (縮退) | 自動処理が止まっても、職員が画面から状況更新・通知できる (受入シナリオ 10) |
| 監視 | App Service のログストリーム。CI で回帰を検知 |
| バックアップ | App Service のバックアップ機能 (SQLite の間)。PostgreSQL 移行後は DB 側の自動バックアップ |
| 更新手順 | GitHub `main` に push → CI → Azure に自動配備。起動時にマイグレーションを適用 |
